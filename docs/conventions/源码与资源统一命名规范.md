# 111 仓库源码与资源统一命名、目录结构规范（权威执行方案）

> 状态：生效／持续执行。制定日期：2026-10-27。适用范围：`sy220284/111` 的 Claude Code 2.1.310 非官方源码恢复工程。此文件是后续命名、目录整理和恢复工作统一遵循的规范。具体每批实际完成与验收情况记录在 [命名规范化改动记录](./命名规范化改动记录.md)。
>
> **最高原则：先保证原版可追溯、功能不回退，再提高可读性。命名规范化不是功能恢复的替代品。** 旧版 2.1.88 是命名、职责和类型的参考；2.1.300 是中间版本佐证；最终必须以 2.1.310 的代码及真实契约为准。

## 一、目标与边界

1. 主程序源码、内嵌代码、资源、工具、技能、插件、模板、文档、类型声明、配置、原生模块及测试**全部纳入**统一管理，不能只整理 `src/chunk-*.js`。
2. 人阅读和维护的工程路径应表达功能与业务归属；原始构建标识、函数短符号、BunFS 键、压缩来源和 SHA256 必须仍可追溯。
3. 每项迁移必须明确原路径、目标路径、调用方、依赖、证据、测试与状态。无法证明安全的保留原位，**不得猜测名称、用旧版代码冒充新版、只替换后缀、留下空实现或用别名掩盖未完成的拆分**。
4. 只处理与当前工作相关的目录与引用；保留 `resources/bunfs/` 的原始资源名作证据层。工程源码不混入原版 ELF、逆向研究日志、历史整仓。
5. 修改现有公共入口／路径时必须修改所有消费者和相应测试；尤其保护插件 manifest、Hook 模块、MCP 标识、N-API 原生依赖与运行时虚拟资源键。

## 二、源文件及目录命名规则

| 对象 | 规则 | 说明 |
| --- | --- | --- |
| 业务函数／模块 | `camelCase.ts/js`（如 `sessionHistory.ts`） | 以已证实职责命名；同名不同职责归不同业务目录 |
| UI 组件与类 | `PascalCase.tsx/ts`（如 `QueryEngine.ts`） | 遵循旧版语义风格，按实际是否需要 JSX 决定后缀 |
| 业务目录 | 简短、稳定的英文业务名称，必要时用 `kebab-case` | 如 `commands/`、`tools/`、`services/`、`components/`、`query/`、`bridge/`、`hooks/`、`plugins/` |
| 工具包／脚本 | `resources/tools/<tool-name>/scripts/<purpose>.mjs` | 原始脚本如含相对导入，必须整体校正并运行 |
| 技能 | `resources/skills/<skill-name>/SKILL.md` | 严格保留 frontmatter `name`、`description`，名称不可与别的技能混淆 |
| 插件 | 独立插件遵循 `.claude-plugin/plugin.json`、`hooks/`、`types/` | 插件运行时、插件实体、测试工具包与示例分开；不能强改插件规定的固定文件名 |
| 文档 | `resources/docs/<topic>/<language>/<document>.md` | 没有语言差异时省略 `<language>`；`README.md`、`SCHEMA.md` 等约定名保留 |
| 模板 | `resources/templates/<purpose>/` 下按模板及资源职责命名 | HTML/CSS/JS 相对路径、引用和动态装载必须联动修订 |
| 内嵌代码 | 能确权后移入相应业务或工具目录 | 保留原始对应关系，禁止为好看而搬迁仍未确权的源码 |
| 类型声明／配置 | 沿用实际消费者要求的 `.d.ts`、`.json` 等约定 | 不把 `types`、manifest、schema 当成普通文档随意改名 |
| 原生组件／字体／三方文件 | 保留 ABI／加载器／许可要求的原名 | 如 `.node`、`.woff2.asset`、已生成的压缩 bundle，不强制改名 |

所有命名以**真实职责**为依据；不要整仓将 `.js` 机械改成 `.ts`。对有差异的文档按语言和用途消除重名，不采用覆盖或任意加序号。

## 三、完整目标分类与现有内容

- `src/`：2.1.310 的 2,551 个主程序模块（含独立 Hook Worker），当前 2,547 个 `chunk-*.js` 应随语义恢复逐批迁移；原短符号对外兼容别名由实际消费者逐步消除。
- `src/embedded/`：24 份已提取内嵌源码；依契约分类，不贸然移动被固定路径引用者。
- `src/plugin-testing-kit/`：294 份已恢复的插件测试辅助源码，维持已有分层和真实导出，不将其误认为所有插件功能已经完成。
- `resources/bunfs/` + `resources/asset-layout.json`：250 份真实原版资源的来源／映射体系，其中 140 份解码后按职责放置；**原 BunFS 键不变**。文件迁移仅更新 `asset-layout.json` 的 `path`，原始 `compressedSha256`、`decodedSha256` 和消费者记录不变。
- `resources/skills/`：每个技能独立目录，规范入口 `SKILL.md`，连同其引用的脚本、模板和说明按功能归集。
- `resources/tools/`：设计、同步、测试、评估、插件 API 等按工具分组；每个含运行代码的文件需检查相对导入、执行命令和资源依赖后再迁移。
- `resources/docs/`、`resources/templates/`、`resources/data/`：按照主题、语言、模板及数据含义分类，保留内容哈希和可回溯键。
- `runtime/`、`tests/`、`scripts/`：运行时适配、对应测试、索引／迁移校验脚本统一维护；源码迁移不能让扫描器漏掉新目录中的文件。

## 四、可追溯性和兼容要求

每次改名必须至少具备 `原路径 → 目标路径 → 对应原版模块／BunFS 键 → 调用方 → 内容或行为验证 → 状态` 记录。对于原本内容完整、只是路径难读的解压 Markdown 文件，允许无损移动：**原文件的 Git blob 不变、SHA256 不变**；程序继续通过原始 BunFS 键查表访问。对于代码模块，需要额外证明导入导出、动态加载、函数调用、异常／取消分支没有发生意外改变。

`resources/manifest.json`、`resources/function-summary.json`、`resources/function-verification-ledger.json` 是各自阶段的证据，不可因改名随意改写哈希或登记状态。源码内容有实质变动时必须重新生成／复核相应索引。不得用“静态链接通过”代替真实功能测试。

## 五、推进次序（不另设并行版本）

**阶段 A：低风险、可验证的目录与文档规范化。** 优先移动已有映射支撑的静态 `SKILL-<hash>.md` 和 Markdown 参考文档，修正同名文档的语言归属。验证原始键、文件 SHA、全部目标路径与技能 frontmatter；保留其他固定原始资源名。本批已执行项详见改动记录。

**阶段 B：工具、模板、内嵌资源和接口分组。** 逐项读取工具脚本、配置与模板的引用；有完整消费者及测试时再规范文件名和目录。插件 manifest、原生模块、ABI／运行时路径优先保留；整理 `src/embedded/` 的已证实职责。不要一次性重命名所有可执行文件。

**阶段 C：主程序语义恢复与按职责拆分。** 依据 2.1.310 函数 AST、静态／动态依赖和 2.1.88／2.1.300 对照，先定义函数职责和边界，再按 `commands`、`tools`、`services`、`components`、`query`、`hooks`、`bridge`、`plugins` 等模块迁移。一个 chunk 可包含多个职责，也可能多个 chunk 构成一个业务模块；**不能机械一对一改名**。未证实的模块保留原名称，允许恢复成果与原始 chunk 在过渡期共存，但不允许双份业务实现悄然分叉。

**阶段 D：统一引用和索引。** 同步检查 `import/export`、`require`、`import.meta.require`、动态 `import()`、BunFS 键、运行时代码、测试 fixture、配置、生成器、脚本及文档链接，迁移索引扫描范围，确保移动目录后模块总数、消费者和函数索引仍完整。

**阶段 E：分批验收与最终整理。** 每批复查文件数、路径唯一性、字节／哈希保真、命名规则、原映射、模块链接和可执行回归；未过验收不得称为恢复完成。进一步进行真实入口、资源装载、Hook／插件／MCP／会话等功能级测试。线上和硬件条件限制须如实标记，不能用假结果代替。

## 六、每批关闭条件

1. **原文件没有丢失或被覆盖**；新增路径与现存路径没有冲突，原始键／来源／SHA 可追溯。
2. **实际所有引用已更新且可解析**；路径映射与模块消费者无断链，动态依赖经过必要验证。
3. **测试真实执行**：受影响的专项检查、`npm test`，必要时 `npm run verify:runtime`；CI 状态记录结果。失败要修复再验收，不能仅声明操作成功。
4. **改动记录同步追加**：列出提交、范围、迁移映射、验证证据、阻碍以及剩余工作；已完成的内容与未实现的功能不混淆。
5. **不得为了命名改变既定源码恢复目标**：优先推进函数、资源和行为的真实恢复，不做没有必要的形式化重构。
